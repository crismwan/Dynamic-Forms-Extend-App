# Dynamic Forms: tiered ownership design (as built)

Built 2026-11-20 from the plan "Dynamic Forms: tiered ownership plan" (phases 0 to 5, the onboarding kit, delivered features and access recommendations; the legal and partner-tenant gate is out of scope). Generated by `tools/build_tiers.py` (new objects and pages), `tools/build_forms.py` (forms, questions, responses, answers, fill pages), `tools/build_studio.py` (Form Studio) and `tools/forms_flows.py` (orchestrations). Status of each item, and what has been tested live, is in `TIERED-PROGRESS.md`.

## How a request gets its form

1. A Service step on the process launches **FormCompose** (actionEvent, processType, worker).
2. FormCompose reads the subject's supervisory organization (`common/v1/workers/<id>`), then its **org map** row: path `|top|...|org|`, department, company, tier.
3. It reads the **block assignments** for the process type and keeps those whose owner covers the subject: scope `org` = the owner org itself, `subs` = the owner or any org below it (its WID is on the subject's path). With no org map row, only enterprise assignments apply.
4. For each matching block family it pins the highest **Published** version, listing them as `tierRank:code` (1 enterprise, 2 department, 3 team).
5. The **compose key** is `processType|pinned list`. An existing composed form with that key is reused; otherwise a Dyn Form of kind `composed` is created with the list in `blocks`. One cached form per combination of process, department and team falls out of this, and a block published mid-request doesn't touch running requests (their composed form names the old versions).
6. It creates (or, after a send-back, reopens) **one assignment** per event: Dyn Response formCode BP, parentKey `FORM:COMPOSED`, with subjectOrg, department, company, pinned versions and processType.
7. On **Onboarding** it also composes the onboarding kit (below).

The fill pages (DynMyFill for employees, DynFormLookup for admins) read the form record; for a composed form they load each block's questions (endpoints b1 to b6), and `df.merge` puts them in one list: enterprise first, then department, then team, each block's own order kept. A question whose **library key** was asked by an earlier block is dropped (asked once; the enterprise copy wins, so the stricter rule applies). Questions that prefill from Workday come first, labelled "Check:". Reusable answers still valid fill the question and the label says so.

**FormGate** then reads the one response's General answers (as before) and writes the route record keyed by the **event** (`TEST:DYN:ROUTE:<event WID>`).

The plan's "Block", "Block version" and "Composed schema" records are all Dyn Form rows (kind empty = block version, `composed` = composed schema), which keeps the app at 14 objects. "Route record" stays a Dyn Response (formCode ROUTE), now keyed by event.

Every new object also lists Use: Dynamic Forms so the tenant's current forms admins and the ISU keep working until the new domains have their own policies; Restricted answers are the exception. Remove Use: Dynamic Forms from an object once its plan domain is set up (a domain change is allowed after promotion).

| Domain | Plan name | Used by |
|---|---|---|

| Dyn Forms Author | Forms: Author | Dyn Assign, Dyn Kit Item; FormAssignments, FormLibrary, FormOwnerDash, KitDesigner, FormPublish |
| Dyn Forms Govern | Forms: Govern | Org map, departments, settings, packages, snapshot; FormGovern and its tools, FormPublish's governance approval |
| Use: Dynamic Forms | Responses: Org view | General answers, responses, forms (today's admin domain) |
| Dyn Confidential Answers | Responses: Confidential | Dyn Answer Confidential |
| Dyn Forms Responses Restricted | Responses: Restricted | Dyn Answer Restricted |
| Dyn Forms Integration | Integration | reserved for the ISU's own grants (orchestrations run as the ISU) |
| Dyn Forms Onboarding Fulfil | Onboarding: Fulfil | Dyn Kit Task, KitQueue |

Contextual security on the subject or owner org (secured by target) is **not** switched on: a secureByTarget field on an object whose existing rows have no target could hide them, and the tenant's groups are user-based. The app enforces the plan's rules itself where it can (below), and the domains above separate the classes.

## Rules the app enforces

| Plan rule | Where |
|---|---|
| 1. Author sets owner org only inside their branch | Not enforced by the app: Extend can't read an author's role assignments per org without broad security reads. Use Author with constrained groups once contextual security is switched on. |
| 2. Team scope stays in one department | FormAssignments (owner and scope onChange) and FormPublish (publishErr) |
| 3. Only governance marks Restricted, publishes enterprise blocks | FormPublish requires the Governance approval tick for enterprise blocks, Restricted questions and department blocks over the reach threshold; the page is open to Author and Govern |
| 4. Only General answers in comments | Structural: FormGate reads Dyn Answer only; protected answers live in their own objects |
| 5. Routing can't be spoofed | Condition: `[ROUTE:HR]` comments **with no Comment by Person** (the ISU's comments have none); see SETUP |
| 6. Integration user scoped to processes with forms | Tenant setup (SETUP) |
| 7. Published versions read only, approver recorded | FormPublish records approvedBy, approvedTier, reachAtApproval, slotCount, approvedOn; FormQuestions saves nothing on a published version |

Prefill and reuse rules: a reused answer keeps its class (only General answers are offered for reuse; Confidential and Restricted are never reused); the person always sees it (label) and can change it; prefill reads Workday as the person filling the form; reuse ends at validUntil or when the location or job title differs from when the answer was given (contextKey), which covers the plan's reset triggers without a nightly job; workers clear answers on My answers.

## Onboarding kit

FormCompose on Onboarding creates, once per event: a **prepare** task for the manager and one task per published **welcome** and **learning** kit item whose owner covers the hire's org (a customer copy replaces the delivered item it overrides). Access items wait for the manager: **KitPrepare** lists every access item that covers the hire's org, with the peers' counts from the snapshot ("Recommended: 4 of 5 peers have it" at 80%+, "Common" at 50%+, nothing under 3 peers; elevated items never ticked and need a reason), and its OK sends each ticked item as a request to its fulfiller group (removed baseline items are recorded with the reason). **KitQueue** shows a group's requests (approve, decline with reason, done; elevated items must be approved first). **KitWelcome** shows the welcome text and the manager's note; **KitGuide** the learning steps. Workday roles are only tracked: the request says to use Workday's own role assignment.

Not built: custom email (the plan's own check; not proven), the daily WelcomeRelease and KitReminders jobs (welcome tasks are created "scheduled"; release by date and reminders need a scheduled orchestration with date arithmetic, see PROGRESS), segregation-of-duties checks (no customer rules to read), and reading Workday role assignments for peers (needs security reads; the snapshot uses the kit's own history, the plan's "safest first" source).

## Delivered features

Three wave-1 packages ship inside the app as JSON (tier.script `pkgs()`): joiner (PKG:JOINER, Onboarding), mover (PKG:MOVER, Change Job), leaver (PKG:LEAVER, Termination). **KitPackages** enables a package (Dyn Package row) and installs its items as Delivered, owned by the top org with scope subs. Delivered items are read only in KitDesigner: Copy to change saves a Customer copy (`code-C`, overrides = the delivered code), which replaces the delivered item for new hires; a later delivered version never touches the copy. The page shows installed items, customer copies and items older than the delivered version. All delivered text is generic and says HR or legal must review it.
